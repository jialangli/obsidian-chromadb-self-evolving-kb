# 混合检索方案

## 为什么单一检索不够

向量检索擅长语义泛化，问"怎么让设备省电"能召回讲功耗优化的段落，但对专有名词很不友好：
型号、错误码、人名、产品代号这些"必须精确匹配"的词，向量往往召回不准。

关键词检索（BM25）恰好相反。它对字面精确匹配极强，但用户换个说法就完全失效，
也理解不了同义词和语义关联。

## 混合检索的优势

把两条通道的结果融合，能同时拿到两边的优点：

- **语义泛化**：用户说法和文档措辞不一致时仍能召回
- **专有名词精确匹配**：型号、错误码、人名不再漏召
- **鲁棒性**：任一通道失效，另一条仍能兜底
- **抗退化**：新词、黑话未进入向量空间时，关键词通道可补位

实测上，混合检索相对单一向量检索的 Hit@5 通常有 10%~20% 的相对提升，
在专有名词密集的知识库（产品手册、故障码表）上收益尤其明显。

## 融合策略

### RRF（倒数排名融合）

最常用也最省事：只依赖排名，不依赖分数，无需归一化。

```
score(d) = Σ  1 / (k + rank_i(d))
```

k 一般取 60，用于压低头部排名差异的影响。两条通道权重相同；
若某通道明显更准，可加权：`w_i / (k + rank_i(d))`。

### 加权分数融合

先把两路分数各自归一化到 [0,1]，再按权重相加。
好处是可精细调节，坏处是归一化方式对结果影响大，调参成本高。

### 两阶段重排（进阶）

先用混合检索召回较大的候选集（如 Top-50），再用 cross-encoder 重排到 Top-5。
cross-encoder 能建模 query 与文档的深度交互，精度显著高于 RRF，代价是多一次推理耗时。
这是当前效果最好的方案，适合对召回质量要求高的场景。

## 实践建议

- 先用 RRF 跑通基线，别一上来就上重排模型
- 建库时把文件名拼进块文本，能让"只出现在标题里的实体"也被关键词召回
- 两通道都保留原始分数，方便事后分析某条结果是被谁捞上来的
- 融合参数（k、权重）要写进配置，不要硬编码在代码里
