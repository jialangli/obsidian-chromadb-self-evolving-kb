# RAG 实践指南

## 什么是 RAG

检索增强生成（Retrieval-Augmented Generation）先检索知识库中的相关片段，再把这些片段作为上下文交给大模型生成答案。
它解决的是大模型"不知道你的私有数据"和"会编造事实"两个问题，成本远低于微调。

## 构建知识库的完整流程

### 1. 数据接入与治理

先确定唯一事实源，再谈索引。实践中最常见的问题是源头混乱：同一个知识点散落在五个文档里且互相矛盾。
建议先做一轮内容治理，用 frontmatter 标注类型、状态、更新时间、可信度，把不可信和过期内容挡在索引之外。

### 2. 分块

按语义边界切分，不要机械地按固定字数切。Markdown 文档推荐按标题层级分块，并把父级标题拼接进块文本保留上下文。
块太小丢失语义，太大引入噪声，中文场景一般 500~1500 字为宜，相邻块保留 10%~20% 重叠。

### 3. 向量化

中文优先选 BGE 系列（bge-small-zh-v1.5 性价比高，512 维）。
查询侧要加指令前缀（如"为这个句子生成表示以用于检索相关文章："），文档侧不加，这是 bge 官方实践。
资源受限或无网络时，可用 TF-IDF + SVD 的 LSA 方案兜底，效果打折但完全离线可用。

### 4. 存储与索引

向量库存向量，同时把原文和元数据一起存进去，检索结果才能直接展示。
关键原则：**向量库是可随时全量重建的派生索引**，源数据才是资产。索引坏了重建即可，不要手工改向量库。

### 5. 检索与生成

检索阶段建议混合召回；生成阶段要求模型标注引用来源，答案不成立时明确说"未找到依据"，而不是硬编。

## 常见坑

- 只优化检索不治理内容：垃圾进垃圾出，换什么模型都没用
- 忽略分块质量：一个块里塞三件事，向量必然不准
- 没有评测集：优化全凭感觉，改完不知道是变好还是变坏
- 用训练集当测试集：指标虚高，上线就露馅
